# === BITNET M6 — energy-per-token (J/tok): BitNet's THIRD headline claim, MEASURED ===
#
# BitNet b1.58 markets THREE headlines: accuracy (M1: FALSIFIED, 30%), memory
# (M2: HOLDS, 0.55x), and ENERGY ("1.58-bit = energy-efficient inference") — the
# energy headline had NEVER been measured on this substrate. M6 measures it:
# energy-per-output-token (J/tok) for BitNet 2B4T (i2_s via bitnet.cpp AND TQ2_0
# via stock llama.cpp) vs the Qwen2.5-0.5B-Q4 SANDBOX stage-0 baseline (16/20),
# IDENTICAL 20-task manifest + byte_exact_subset scorer as M1/M2/M2+.
#
# bench: bench/bitnet_m6_energy_per_token.hexa  (cx_empirical_contact T4, $0 local)
# host : mac-mini-m3 (Mac15,12, 24 GB UMA), 2026-05-25
#
# ============================================================================
#   MEASUREMENT METHOD (FULL FIDELITY — hardware power meter, NOT a proxy)
# ============================================================================
# `sudo -n powermetrics --samplers cpu_power,gpu_power -i 200` ran as a
# background sampler for the WHOLE 20-task run, logging "Combined Power
# (CPU + GPU + ANE): NNNN mW" every 200 ms. This is the REAL whole-SoC wall
# power on the hardware meter — it captures BitNet's CPU-only path AND Qwen's
# Metal-GPU path on the SAME scale (the decisive property: a CPU-seconds proxy
# would have understated the GPU baseline; we did NOT need the proxy — sudo
# powermetrics was available passwordless).
#   Energy(J) = Σ_samples (combined_mW / 1000 W) * (200/1000 s)
#   Output tokens = EXACT, from the llama perf trailer "eval time = ... / N runs"
#                   (N decoded tokens), NOT a wc-estimate.
#   J/tok = Energy / Σ output_tok.
# Two readings are persisted per model:
#   - GROSS  = whole-SoC energy over the sampler window / tokens (idle-inclusive).
#   - THRU   = mean_W / throughput(tok/s) — the LOAD-INDEPENDENT per-token energy,
#              robust to wall-time / idle variance (THE comparable headline number).
# FIDELITY CAVEAT (honest): powermetrics meters the WHOLE machine. On a non-
# isolated desktop, background OS power (~4-5 W idle) is the same magnitude as a
# fast run's draw, so the IDLE-SUBTRACTED "net" reading is UNRELIABLE (clamps to
# ~0 when an inline idle sample exceeds the run mean) — it is reported only as a
# fenced lower bound. GROSS and THRU are the load-honest metrics; THRU decouples
# from idle entirely (power / throughput) and is the verdict's headline.
#
# ============================================================================
#   RESULT — J/tok COMPARISON (run-set 2; arithmetic verified EXACT below)
# ============================================================================
#   model                       acc    mean_W   wall_s    tok   tok/s   J/tok(thru)
#   --------------------------- ----   ------   ------   -----  ------  -----------
#   Qwen-0.5B-Q4  [Metal GPU]   80%    5.087     26.3     348   13.22      0.385   <- baseline
#   BitNet-i2_s   [CPU-only]    30%    5.193    254.1    1900    7.48      0.695
#   BitNet-TQ2_0  [CPU-only]    30%    4.353    165.4    1152    6.96      0.625
#
#   ratio BitNet-i2_s  / Qwen  = 1.81x  (BitNet 1.58-bit uses 1.81x MORE J/tok)
#   ratio BitNet-TQ2_0 / Qwen  = 1.62x
#
# DECISIVE FINDING: On THIS substrate BitNet b1.58 2B4T consumes 1.6-1.8x MORE
# energy-per-token than the 4-bit Qwen baseline — its headline energy-efficiency
# claim is FALSIFIED here. The mechanism is unambiguous: SoC POWER is ~equal
# (~4.4-5.2 W) whether running BitNet's CPU path or Qwen's Metal path (the M3 SoC
# draws roughly the same watts either way); the difference is entirely
# THROUGHPUT — Qwen 13.2 tok/s on Metal GPU vs BitNet 7.0-7.5 tok/s CPU-only.
# BitNet's ternary kernel has NO Metal GPU implementation on this substrate, so
# it runs CPU-only at ~half the throughput -> ~1.7x the energy per token.
# BitNet's marketed energy advantage assumes a TERNARY-OPTIMIZED ACCELERATOR
# (a substrate where {-1,0,+1} MAC-free arithmetic cuts both ops AND power);
# this substrate has no such accelerator, so the theoretical advantage is ERASED
# — running on the wrong hardware turns a claimed win into a 1.7x loss.
# Combined with M1 (accuracy FALSIFIED 30%) and M2 (memory HOLDS 0.55x): of the
# three headlines, only MEMORY survives on this substrate; ACCURACY and now
# ENERGY both fail.
#
# === claim test: '1.58-bit = energy-efficient inference' on THIS substrate ===
