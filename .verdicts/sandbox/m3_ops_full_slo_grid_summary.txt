# ── primary finding 2: TWO distinct accuracy-cliff mechanisms ───────────
# M2.OPS reported an accuracy collapse 88%→19.75% under saturation and attributed
# it to curl --max-time 30 truncating slow completions (p99 > 30s → empty body →
# byte-exact WRONG). The full grid REFINES this into two separable mechanisms:
#
#   (a) TIMEOUT-truncation cliff (M2.OPS mechanism): needs p99 > req_timeout (30s).
#       NOT triggered in this run — every cell's p99 stayed < 11.5s (the np=1 cells
#       capped at p99 ~10–11s, still under 30s), so np=1 accuracy holds 86–94%.
#   (b) SLOT-PREEMPTION cliff (NEW, np≥2): at high offered rate the continuous-batch
#       scheduler preempts/early-stops in-flight generations to admit new arrivals,
#       returning SHORT-but-HTTP-200 content that fails byte_exact_subset. This is
#       why np=2/np=4 accuracy collapses at rate≥20 (np=2: 94→53.82→29.03%; np=4:
#       94→41.50→19.26%) DESPITE p99 staying well under the 30s timeout and
#       error_rate staying 0.00% (all responses are HTTP 200 — the failure is in
#       CONTENT completeness, not transport). n_correct confirms: np=4 rate=40 has
#       n_completed=1225 but n_correct=236.
# Combined OPS law: an offered-load SLO violation surfaces as an ACCURACY cliff via
# whichever truncation path the deployment exposes first — client timeout (a) at low
# -np / long tail, or scheduler preemption (b) at high -np / high concurrency. A
# latency-only SLO dashboard would miss BOTH; the correctness axis is mandatory.
